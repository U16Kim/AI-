# 資料作成の基準

依頼者（自治体の課長。まちづくり・政策企画・官民共創）向けの、見た目を伴う成果物の作成基準。

**大原則：デザインは「前回の見た目」ではなく、「今回の内容・読み手・使われる場面」から毎回導く。** 題材と表現を混同しない（AIの話だから回路柄、量子の話だから星雲、都市の話だから俯瞰写真、は考えていない証拠）。依頼者の基準は「視覚的なインパクトは出す。ただし、上品さを欠くことは許されない」。

## 1. 手順（この順に行う）

1. **型を判定する**（2節）。複数に当たるなら、主となる型を選ぶ。
2. **読み手・場・立場を具体にする**：誰が（市長／局長／議会／市民／企業）、どこで（会議室の投影／手元の印刷／スマートフォン）、その場で何をするか（聞く／議論する／決裁する／持ち帰る）。こちらは、お願いする側か、魅せる側か、説明責任を負う側か。
3. **一次情報を先に集める**（調べるのが先、書式は後）。数値は、出典と時点を控える。
4. **設計図を文章で作る**：`logic-storyline` で、Ask・問い・結論・根拠3つ・反論への備え・見出し・30秒版を決める。会話で既に決まっていれば、それを使う。スライドを作り始めない。
5. **デザインを3案、1〜2行ずつ言葉で示し**、推奨を1つ選んで進める（5節）。理由を言えないデザインは、内容から導けていない。重要案件は、表紙と施策体系図の2枚だけを3案で試作してよい。
6. **作る**：型B・C・Dは3〜4節と `references/design-system.md`、型A・F・Eは `references/rich-visual.md`。PPTXは `scripts/lib.js` の部品を使う（`references/pptx-components.md`）。
7. **確かめる**（7節）：描画して全頁を目視 → `audit.py` → `validate.py` → `deliverable-verifier`。

足りない情報は、まとめて1回だけ聞く（最大3項目：決めてほしいこと／持ち時間／印刷か投影か）。会話で決まっていれば聞かない。

| 参照ファイル | 内容 | 読むとき |
|---|---|---|
| `references/design-system.md` | 活字の尺度・色・余白・線・面の設計値（唯一の正）、主役と山場、定型の部品、使わないもの、重要案件の検証の進め方 | 型B・C・Dを作る前。型A・F・Eでも尺度と色は従う |
| `references/pptx-components.md` | `lib.js` の使い方と部品の一覧、pptxgenjs の地雷、描画と実機の差、監査の目安 | PPTXを作る前 |
| `references/rich-visual.md` | 型A・F・Eの質の基準、画像の使い方と生成の技法、HTMLの決まり、中身の質、点検表 | 講演・広報・技術解説・HTMLを作る前 |
| `scripts/lib.js` | 検証済みのレイアウト部品（体系図・スイムレーン・手順・工程表・比較表・期限札ほか） | PPTXを作るとき、作業フォルダにコピーして使う |
| `scripts/audit.py` | 尺度・太字・コントラスト・濃色の枚数の監査 | PPTXを作った後、必ず |

## 2. 型の判定

| 型 | 目的 | 読み手の行動 | 地 | 画像 | 主役 |
|---|---|---|---|---|---|
| **A ビジョン・説得** | 心を動かす | 「やろう」と思う | 暗色も可・余白大 | 内容を語るものだけ | 言葉（コピー） |
| **B 意思決定・判断** | 選ばせる・承認させる | 決裁する | 白 | 使わない | 比較表・体系図・数字 |
| **C 実務協議・依頼** | 認識をそろえ、宿題を頼む | 持ち帰って動く | 白・文書的 | 使わない | 工程表・流れ・依頼の一覧 |
| **D 報告・記録** | 正確に伝える | 読み返す | 白 | データの図表だけ | 見出しの階層と図表 |
| **E 技術・分析の解説** | 理解させる | 分かる | 白 | 説明のための概念図 | 図解 |
| **F 祝祭・広報・集客** | 高揚させる | 来場する・広める | 自由 | 主役になりうる | ビジュアル |
| **G 危機対応・謝罪** | 信頼を保つ | 安心する | 白・無彩色 | 使わない | 事実と時系列（朱も使わない） |

- **市長・社長・幹部への政策説明は、原則としてB（決裁）かC（協議）。**
- **印刷・回覧される資料は、白い地が絶対**（暗い地はトナーを食い、書き込めず、コピーでつぶれる）。
- お願いする側・説明責任を負う側が華やかな演出をすると、中身の薄さを隠しているように見える。**抑えることが、誠実さの表現**になる。
- 一貫性は、要素（ロゴ・差し色・フッタの文言・用語）でそろえる。毎回同じ見た目にする必要はない。

**全ての型に共通する禁止事項**

- 前回の資料の見た目の流用／題材からの短絡／内容と関係のない装飾画像／暗い地と光のにじみを「高級感」として汎用に使うこと
- 絵文字（環境によって表示されない）／図形の影・図形のグラデーション／タイトル下の線／端の細い色帯・縦の縞（安っぽく見える典型）
- 箇条書きだけの頁。必ず、図・表・大きな数字のいずれかを置く
- 情報の密度が要る表を、余白優先で読みにくくすること（逆に、気持ちに訴える場面で表を並べることも誤り）

## 3. 政策説明スライドの組み立て（型B・C・D）

設計図（`logic-storyline`）を、次の決まりでスライドにする。

- **タイトルは結論の文**（例：「手続を一本化し、最短10日で実施できる体制にする」）。「現状と課題」「施策の概要」のような名詞だけのタイトルは使わない。全角40字以内、2行まで。タイトルだけを順に読んで、話が通ること。
- **1スライドに、言いたいことは1つ。** 2つあるなら2枚にする。
- **主張 → 図表 → 留保**の順。「ただし、こう読むべき」を1行添える。推計・目標値は「実績ではない」と書く。
- 選択肢には「やらない」「延期」を入れる。推奨は1つ、理由は3つ以内。
- 事例を入れる（国内外1〜3件。成功と失敗の両方）。川崎市の事実は `kawasaki-admin-reference`、東京都・横浜市は `metro-gov-reference` の確認済みのものを使う。

**標準の構成**（持ち時間 ÷ 1.5〜2分 ＝ 本編の枚数。細部は参考資料へ回す）

| 順 | スライド | 役割 |
|---|---|---|
| 1 | 表紙 | 件名・日付・所属 |
| 2 | **サマリー（結論＋Ask）** | 30秒で、全体と依頼事項が伝わる |
| 3 | 現状と課題 | データ1〜2点＋「だから何か」を1行 |
| 4 | 基本方針・目的 | 何を目指すか |
| 5 | **施策体系図** | 目的→施策の柱→事業→指標 |
| 6 | **施策フロー** | 誰が・いつ・何をするか |
| 7 | 選択肢の比較 | 2〜3案＋やらない案。推奨を示す |
| 8 | 効果・KPI／財政影響 | 数字を大きく |
| 9 | リスクと対応 | 上位3つ |
| 10 | **スケジュール** | 関門（決裁・議会・予算）を強調する |
| 11 | 体制・役割分担 | 主体×役割 |
| 12 | **Ask・次の一歩** | 決めてほしいこと／期限／持ち帰り事項 |

説明は、30秒版・3分版・10分版を用意し、各スライドの `addNotes()` に台本を入れる。想定問答は別紙にする（中身は `exec-council-stakeholder-comms`）。

**相手別の注意**

- 市長・局長：結論とAskを2枚目までに。想定問答を別紙で用意する。
- 民間の経営層：投資に対する効果（金額・回収の期間・リスク）を数字で。行政の用語を、事業の用語に言い換える。
- 印刷・回覧：白い地。A3をA4に縮めても読めるか確かめる（本文は14pt以上を保つ）。

## 4. 図の選び方と作法

| 伝えたいこと | 使う図 | 部品（`lib.js`） |
|---|---|---|
| 施策の全体像・なぜこの事業か | **施策体系図**（目的→柱→事業→指標） | `tree` |
| 誰がいつ何をするか／事務の流れ | **スイムレーン**（主体×段階）、路線図 | `swimlane`／`box`+`badge`+`arrow` |
| 段階的な進め方 | **手順の流れ**（番号＋担当） | `flow` |
| 効果に至る筋道（EBPM） | **ロジックモデル**（投入→活動→産出→成果） | `flow` を5列に |
| 官民の役割、お金・サービスの流れ | **事業スキーム図**（主体を箱に、矢印に「何が動くか」） | `box`+`arrow` |
| 案の選択 | **比較表**（評価軸×案。推奨を色で） | `options` |
| 時間・関門 | **工程表**（関門を強調色、未確定は破線） | `roadmap` |
| 役割分担 | **役割表**（主体×役割×期限） | `addTable` |
| 判断の分かれ道 | **判断の流れ**（条件を書いた分岐） | `box`+`arrow` |
| 期限・目標値 | **期限札**、数字＋単位 | `plate`／`numline`／`tag` |

- **流れは一方向**（左→右、または上→下）。逆流・交差する矢印を作らない。矢印が箱を貫かない。
- **1つの図で言うことは1つ。要素は5〜9個。** 超えるなら分けるか、上位の概念でまとめる。
- **「誰が」を必ず書く**（担当の箱・レーン）。主体のない手順は、実行されない。
- 手順は**動詞で始め**（「申請する」「審査する」）、番号を振る。
- **色の意味を固定する**：主色＝通常の主役、朱＝関門・Ask・推奨・期限だけ（1頁2か所まで）、グレー＝補助。凡例がなくても読めること。
- **矢印の意味は1種類**（時間・因果・お金のどれか）。複数あるなら、線種と色を変え、説明を付ける。
- **線種で確かさを語る**：実線＝確定、破線＝未確定・目標。数値を、図形の大小や高さで暗示しない。
- 図の中の文字は14pt以上（図の注と表の本文だけ12pt可）。入らなければ、文言を削る。
- 図は図形で作る（画像にしない）。受け取った人が自分で直せる。
- 出典と時点を、各スライドの下に10.5ptで置く。

**設計値の要点**（詳細と理由は `references/design-system.md`。食い違ったら、そちらが正）

| 項目 | 値 |
|---|---|
| 文字サイズ | 10.5／12／14／17／21／25／30／36／43／62／89／107／185pt だけ。本文14、タイトル30、主役62〜185 |
| 太字 | タイトル・見出し・ラベルだけ。全体の4割以下。主役の大字は標準ウェイト |
| 書体 | 本文は Meiryo。主役の大字は、日本語が游明朝、数字・欧文が Cambria |
| 余白 | 左右0.75インチ。本文の領域は縦1.9〜6.9。左端を全頁でそろえる |
| 色 | 白（紙色 `F4F6FA`）＋ネイビー `1F3A5F`＋朱 `B93A14`（濃色面は `F28A62`）。主色は内容から導いて差し替えてよい |
| 全面濃色 | 夜色 `0B1730`。表紙＋山場2枚の3枚まで（付録の扉を置く場合は4枚） |
| 主役 | 1頁に1つ。他の要素の3倍以上の大きさ |
| 期限札 | 同じ語・同じ色・30pt・幅3.1インチを、全頁で同じに |
| 画像（型B・C・D・G） | 使わない。表紙・扉も、色面と活字で作る |

## 5. デザイン3案の出し方

内容・読み手・場面から、方向を3つ言葉にして示し、推奨を1つ選ぶ。下の4つは出発点であり、内容に合わせて作り変える。3案は、互いにはっきり違うものにする。

| 方向 | 向く場面 | 特徴 |
|---|---|---|
| 端正な行政文書型 | 局長・市長への決裁・協議（型B・C） | 白い地。罫・表・図が主役。朱は関門だけ |
| エディトリアル型 | 市長への方針説明、外部講演の本編 | 大きな結論の文、広い余白、巨大な数字、図は少数精鋭 |
| 夜色×活字型 | 市長・副市長への山場の方針説明（型B。投影し、白い版を印刷） | 画像なし。本編の大半は紙色、濃色は表紙＋山場2枚。主役は細い書体の巨大な活字、図は路線図、朱は期限札・関門・推奨だけ |
| 投影重視の暗色型 | 暗い会場での外部発表（型A） | 暗い地、白の大きな文字、強調色1つ。印刷しない場合だけ |

## 6. 型A・F・E（講演・広報・技術解説）とHTML

`references/rich-visual.md` を読んでから作る。要点：

- 全ての面に、内容を説明する視覚要素を置く。**枚数ではなく、「何を説明しているかを1文で言えるか」で判断する。**
- 画像は、渡された素材 → データから作る絵 → 図形と活字の概念図 → 生成画像（光・流れそのものが内容の場合だけ）の順に検討する。
- HTMLは1ファイルで完結させ、スマートフォンで、ダークでもライトでも読めるようにする。
- 文字の尺度・太字・色の釣り合いは、型B・C・Dと同じ設計値に従う。
- 中身の質（主張→図表→留保、出典、川崎市・まちづくりへの意味合い、時間軸ごとの行動）は、視覚と同じ重さの要件。

Word・PDFの文書は、本文10.5pt以上、見出しは階層が上がるほど大きくする。技術的な作り方は、それぞれの形式のスキル（`docx`・`pdf`）に従う。

## 7. 確かめる（省略しない）

```bash
# 誰が：作成者（Claude）が／どこで：作業フォルダで／何を：作ったPPTXを／どうする：検査し、全頁を画像にして見る
python3 audit.py out.pptx --dark 1,8,12                                   # 尺度・太字・コントラスト・濃色の枚数
python3 <pptxスキル>/scripts/office/validate.py out.pptx                  # ファイルの健全性
python3 <pptxスキル>/scripts/office/soffice.py --headless --convert-to pdf out.pptx
pdftoppm -jpeg -r 100 out.pdf s                                          # 全頁を画像にする → 一覧にして必ず目で見る
```

見る点：文字のはみ出し／要素の重なり／矢印が箱を貫いていないか／1字だけの折り返し／軸の負の値／縞／余白の不ぞろい。HTMLは、タグの対応と、スマートフォンの幅・ダークとライトの両方での見え方を確かめる。

最終の見た目は PowerPoint の実機で確認するよう、依頼者に伝える（こちらの描画は書体が違い、幅がずれる）。

**完成前の点検（型B・C・D。型A・F・Eは `references/rich-visual.md` の点検表も）**

- [ ] 型と、デザインの理由を、1行で言える
- [ ] Askが、2枚目のサマリーと最終枚にある（決めてほしいこと・期限）
- [ ] タイトルだけを通読して、話が通る。1スライドに言いたいことは1つ
- [ ] 文字だけの頁がない。図の要素は9個以内。体系図と流れに「誰が・いつ・何を」がある
- [ ] 選択肢に「やらない／延期」があり、推奨の理由は3つ以内
- [ ] 数値に出典と時点がある。目標値には、同じ行に「（目標）」がある。留保が添えてある
- [ ] 全頁に主役が1つあり、縮小（幅320px）しても主役が見える
- [ ] 朱は、関門・Ask・推奨・期限だけ。期限の語が、全頁で同じ言い方・同じ色・同じ大きさ
- [ ] 画像・アイコン・絵文字・影・縦書き・黄色・飾りの帯がない。印刷・回覧する版は白い地
- [ ] `audit.py` が全項目で目安の内（尺度外なし、太字4割以下、コントラスト不足なし、全面濃色3枚以内）
- [ ] 全頁を描画して目で見た。`validate.py` が通った
- [ ] `deliverable-verifier` で、数値・出典・論理を検証した
