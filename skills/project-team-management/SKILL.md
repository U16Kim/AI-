# プロジェクト運営・チームマネジメント

対象ユーザーは川崎市の課長級職員。プロジェクトを期限内に動かし、部下を育てながら成果を出すための、実務の型を提供する。

## 最初にやること

依頼を次の6つのモードに振り分ける。複数にまたがる場合は、順に処理する。

| モード | 典型的な依頼 |
A 全体スケジュール | 「工程表を作って」「いつまでに何をやるべきか」
B 推進体制 | 「体制を考えて」「誰を巻き込むべきか」
C 部下の意思決定依頼 | 「部下から〇〇でよいかと聞かれた」
D 業務目標設定 | 「期首の目標を考えたい」
E 業務量把握 | 「誰にどれだけ仕事が偏っているか」「定数要求の根拠」
F 人事評価 | 「評価コメントの下書き」「面談の準備」

不足情報は、まとめて1回だけ質問する（最大3項目）。推測できるものは「前提」として明記して先に進む。

## 共通ルール

- 最初に「概略」を簡単な日本語で、次に詳細を書く。
- 事実・推測・意見を区別する。確認できない制度・日程・様式は「要確認」と書く（作り話をしない）。
- 日付・曜日・日数はPythonで計算する。目分量にしない。
- 政策・事業の推進では、国内外の類似事例を1つ以上添える（他都市の体制・工程）。
- ユーザーの案に矛盾や甘さがあれば、はっきり指摘し、より良い案を1つ示す。
- 工程には、法定の手続（都市計画の縦覧、議決、公募期間、許認可の標準処理期間）を先に置く。期間が分からない手続は「要確認」とし、確認先を書く（制度は `urban-development-practice`、条文は `japan-law-research`）。
- 進み具合の指標（件数、日数、達成率）を1〜3個決め、月次で見る。効果の測り方は `data-science-foundations`。

## モードA: 全体スケジュール

### 手順
1. **ゴールの固定**: 最終ゴール（事業開始日、議決日、決裁日、イベント当日など）と、動かせない日付を確認する。
2. **逆算**: ゴールから逆に、必要な工程を並べる。
3. **行政特有の前提を入れる**（日程は年度ごとに変わるため、必ず一次情報で確認する）
   - 予算: 要求・査定・議決の時期、補正予算の可否（確認済み・令和9年度予算編成方針、2026-08-24公表: 11月 オータムレビュー → 12月中旬 内示 → 1月中旬 市長査定 → 2月上旬 公表。年度ごとに変わるため、次年度は新しい方針で確認する）
   - 議会: 定例会・委員会の日程、議案提出の締切（川崎市議会の公式サイトで確認）。確認済みの会期: 令和7年第4回は2025-11-26〜12-22、令和8年第2回は2026-06-01〜06-24。令和8年第4回は未確認（要確認）
   - 庁内協議: 財政、法制（法規）、関係局、総務、デジタル関係等への協議・合議の期間
   - 契約: 公募・プロポーザル・入札の標準日数、契約の締結時期
   - 補助金等: 公募→審査→交付決定→実績報告→額の確定→支払
   - 年度またぎ: 繰越、債務負担行為、国費の内示時期
4. **クリティカルパス**を特定し、遅れると全体が遅れる工程に赤印を付ける。
5. **バッファ**: 庁内協議と外部調整の工程に余裕日数を入れる（根拠付き）。
6. **外部依存リスク**: 国・県・民間・議会など、自分で動かせない日付を一覧にする。

### 出力
- マイルストーン表（日付・内容・責任者・根拠）
- ガントチャート（HTMLまたはExcel。スマホで見る場合はHTML）
- 協議・決裁が必要な先の一覧
- 遅延リスクTOP5と先手の対応

## モードB: 推進体制

### 手順
1. 事業の目的と、必要な意思決定の種類（庁内決裁・議会・外部合意）を整理する。
2. **RACI表**を作る（実行R・説明責任A・相談C・報告I）。人名ではなく役割で書く。
3. 会議体を設計する（名称・目的・頻度・参加者・決めること・決めないこと）。
4. 窓口を一本化する（外部からの問い合わせ先、庁内の取りまとめ役）。
5. 部下の分担案を作る。モードEの業務量と必ず突き合わせる。
6. 他都市事例（体制図・会議体）を1〜3件示す。

### 弱点チェック
- 責任者が不明な工程はないか。
- 1人に集中していないか。
- 意思決定の遅れが出る会議体になっていないか。

## モードC: 部下の意思決定依頼への応答

### 手順
1. 依頼を分類する: 承認依頼／方針相談／助言依頼／上位へのエスカレーション相談。
2. 判断の重さを見る。予算・対外関係・法令・議会に関わる、または後戻りできない場合は、`decision-support` スキルで分析する。
3. 次の形で返答案を書く（部下にそのまま送れる文面）。

```
【結論】承認する／条件付きで承認／再検討して再提出
【理由】根拠を2〜3点
【条件・期限】いつまでに、何を満たすか
【あなたの次の行動】誰に何をするか（1〜3個）
【上に上げる要否】課長・室長として私が行うこと
```

### 守ること
- 結論だけでなく、**判断基準**を一緒に伝える（次回から部下が自分で判断できるようにするため）。
- 部下の案の良い点を1つ、具体的に認める。
- 部下の権限を超える内容は、誰が決めるかを明示する。
- 法令・個人情報・公平性に関わる点は、必ず確認事項として書く。

## モードD: 業務目標設定

### 手順
1. 上位の目標（総合計画、局・室の運営方針、重点事業）を確認し、つなげる。
2. 部下ごとに、次の3種類に分けて設定する。
   - 成果目標（何が変わるか。数値や状態で書く）
   - 行動目標（どう仕事を進めるか）
   - 成長目標（身につける能力）
3. 各目標に「達成の姿」を書く。評価時に、達成・未達を事実で判断できる粒度にする。
4. 難易度を調整する: 現在の力量より少し高く、年度内に実現できる範囲にする。
5. 人事評価制度の定めに合わせる。確認済み（川崎市職員の人事評価の実施に関する要綱。事務・技術職員）: 業務目標は3個または4個、各目標に難易度（A〜D）とウエイトを付ける（第11条）。達成度はT1〜T5の5段階。目標設定は4〜5月（目標設定面談）。様式は第1号様式。要綱の最新の改正は未確認なので、使う前に人事給与のページで確認する（要確認）。出典は `kawasaki-admin-reference` の「人事評価」。

### 弱点チェック
- 数値化しやすい目標だけに偏り、重要な質の目標が抜けていないか。
- 部下間で難易度が極端に違わないか。
- 業務目標が要綱の個数（3個または4個）に収まっているか。行動目標・成長目標は、能力評価の項目（別表第8〜第10）との対応を確認する（要確認）。

## モードE: 業務量把握

### 手順
1. 業務を一覧にする: 定常業務／プロジェクト業務／突発・調整業務。
2. 業務ごとに、月あたりの想定工数（時間）と、繁忙期を入れる。
3. 管理職の観察メモ（日々の様子、会議、依頼の量）を根拠として使う。自己申告だけに頼らない。
4. 人ごとの月別負荷（ヒートマップ）を作り、偏りを見つける。
5. 平準化案を出す: 業務の移管、期限の調整、外部委託、定数要求の根拠としての整理。

### 注意
- 工数は推計であることを明記する。実績データがあれば、推計と比べる。
- 数値は個人の評価に直結させない。業務の構造を見るために使う。
- 個人に関する情報はこの会話内で扱い、不要な外部共有をしない。

---

## モードF: 人事評価（下書き支援）

### 手順
1. 評価期間中の**事実**（行動・成果・場面）を集める。観察メモ、成果物、会議記録を使う。
2. 事実を目標と照らし、達成度の**案**を作る（最終判断は課長が行う）。
3. フィードバックを3部構成で下書きする: 良かった点／課題／次期に期待すること。
4. 面談の進め方を作る: 本人の自己評価を先に聞く、事実で話す、次の一手を一緒に決める。
5. 評価区分は要綱に従う。確認済み: 最終評価は5〜1の5段階（第15条）、業績評価の達成度はT1〜T5。標準点は業績評価・能力評価ともに50点（事務・技術職員）。係長・係員の最終評価は、5は上位10分の1以内、5と4を合わせて上位10分の3以内（別表第11。少人数の特例は別表第12）。手続は別表第4: 評価実施期間は1〜3月で、自己申告 → 評価時面談 → 1次評価 → 2次評価 → 確認 → 結果通知 → 最終評価決定。チャレンジ提案が優秀、または身近な改善に効果があれば、能力評価に1点加算（第12条）。達成度等の評価情報は非公開（第16条）。「S・A・B」の区分は、この要綱の本文では確認できない。要綱の最新の改正と様式の中身は未確認（要確認）。

### バイアス点検（毎回行う）
- 直近の出来事に引きずられていないか。
- 印象が強い1つの事実で全体を判断していないか。
- 自分と似た人を高く評価していないか。
- 全員を甘く、または厳しくしていないか。

### 注意
- 評価は人の処遇に関わる。下書きは必ず本人が責任を持って確認・修正する前提で出す。
- 事実の根拠がない評価文は書かない。足りない事実は「要確認」と書く。
- 評価結果の個別情報は、メモリや外部サービスに保存しない。
