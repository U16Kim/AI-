## 1. 制度スキームの選定（軽い順）

**原則：軽い制度から検討する。** いきなりPark-PFIを勧めない。
小さな担い手にとって初期投資の大きい制度は、勝てないだけでなく、
勝っても事業が続かない。

| 重さ | 制度 | 向く場面 | 初期投資 | 期間 |
|---|---|---|---|---|
| 軽 | 行為許可（条例） | 単発イベント | ほぼ無し | 数日 |
| 軽 | 行政財産の目的外使用許可 | 建物の一部を定期的に使う | 小 | 1年更新が多い |
| 中 | 都市公園法 第5条 設置管理許可 | 公園に小規模な施設を持つ | 中 | 上限10年（更新可） |
| 中 | 指定管理者 | 施設の運営全体を担う | 中 | 3〜5年が多い |
| 重 | Park-PFI（公募設置管理制度） | 収益施設＋公共部分の一体整備 | **大** | 上限20年 |
| 重 | PFI（PFI法） | 大規模な施設整備 | **大** | 10〜30年 |

### 選定の質問
1. 単発か、継続か → 単発なら行為許可で足りる
2. 建物を建てるか、既存を使うか → 建てるなら一気に重くなる
3. 収益を伴うか
4. 担い手の資金力はどのくらいか
5. どのくらいの期間やりたいか

**小さな担い手への現実的な推奨経路：**
単発の行為許可で実績をつくる → 目的外使用許可で定期化する →
設置管理許可または指定管理へ。いきなり最上段を狙わせない。

## 2. 採択条件の逆算

### 募集要項がある場合
1. 評価項目と配点を全て抽出し、表にする
2. **配点の大きい順に並べ替える**（ここが最重要。多くの応募者は
   自分の得意な項目に紙幅を割いてしまい、配点の大きい項目が薄くなる）
3. 各項目について、要項が何を求めているかを平易な日本語に翻訳する
4. 失格要件（応募資格、必須提出書類、様式）を別枠で抜き出す
   — **失格は最も多い落選理由であり、かつ最も防ぎやすい**

### 募集要項がまだ出ていない場合
同種の他自治体の要項から評価項目を推定する。
推定であることを必ず明示し、確定後に見直す前提で作業する。

### サウンディング（対話型市場調査）
公募前に自治体が実施する対話の場。**小さな担い手ほど参加すべき**。
参加すると、①要項に自分の得意分野が反映される可能性がある
②担当者に顔と意図が伝わる ③要項の意図が読める。
参加の有無を必ず確認し、未参加なら次の機会を勧める。

## 3. 採択スコアリングの設計と実装

### 位置づけ
これは**弱点を見つけるための道具**であり、当落を予測する道具ではない。
「◯◯%の確率で採択される」という断定的表現は使わない。

### 設計
評価項目 × 配点 × 現状の充足度（0〜1）で期待得点を出し、
「配点は大きいのに充足度が低い項目」＝**最優先の補強対象**を特定する。

```python
# 誰が：応募を検討する担い手（または支援する木村さん）が
# どのアプリで：JupyterLab または Google Colab で
# 何を：募集要項の評価項目と現状の充足度を
# どうする：期待得点に換算し、補強すべき項目を優先順に出す

import pandas as pd

# 募集要項から抽出した評価項目と配点、および現状の充足度（0〜1で自己評価）
items = pd.DataFrame([
    # 項目名,                配点, 充足度, 根拠メモ
    ("公園の魅力向上への寄与",  30, 0.6, "コンセプトは明確だが定量的な効果が未記載"),
    ("事業の安定性・実現性",    25, 0.3, "資金計画が弱い。金融機関の与信なし"),
    ("地域との連携",           20, 0.9, "地元3団体と協定済み"),
    ("維持管理の考え方",        15, 0.5, "体制は書けるが人員が未確定"),
    ("収支計画の妥当性",        10, 0.4, "根拠となる需要推計が薄い"),
], columns=["項目", "配点", "充足度", "メモ"])

items["期待得点"] = items["配点"] * items["充足度"]
items["伸びしろ"] = items["配点"] * (1 - items["充足度"])   # 補強で取り返せる点数

total = items["配点"].sum()
print(f"想定得点: {items['期待得点'].sum():.1f} / {total}")
print("\n■ 補強の優先順位（伸びしろが大きい順）")
print(items.sort_values("伸びしろ", ascending=False)[["項目", "配点", "充足度", "伸びしろ", "メモ"]]
      .to_string(index=False))
```

**コードの解説：**
- 「伸びしろ」は、その項目を完璧にしたときに増える点数。
  配点が大きく充足度が低い項目ほど大きくなる。
  ここが大きい順に手を入れるのが、最も効率のよい書類改善になる。
- 充足度の自己評価は甘くなりがち。**必ず第三者（または審査員視点の
  Claude）が採点し直す**こと。

### ⚠️ ロジスティック回帰による採択確率推定について
過去の公募結果データ（応募者属性・提案内容・採否）が十分に集まれば、
ロジスティック回帰で採択確率を推定するモデルを構築できる。ただし：
- 公募ごとに評価基準が異なるため、汎用モデルの精度は期待しにくい
- サンプル数が少ないと過学習する
- **データが揃うまでは上記の期待得点方式で運用する**

モデル構築に進む場合は、必ず交差検証と、係数の解釈可能性を優先すること。
予測精度より「どの要素が効いているか」が担い手にとっては有用である。

## 4. 応募書類の型

```markdown
# [事業名]（提案書）

## 1. 提案の要旨（1ページ）
- この提案で、この場所がどう変わるか（1文）
- 誰の、どんな困りごとが解決するか
- 提案者は何者で、なぜできるのか

## 2. 現状認識と課題
- 対象の場所の現状（データで示す）
- 自治体の上位計画との整合（総合計画、緑の基本計画、公共施設等総合管理計画等）
  ※ 上位計画の引用は必須。審査員は必ず見る

## 3. 事業コンセプト
- コンセプトを一言で
- なぜこの場所でこれなのか（場所の固有性との結びつき）

## 4. 事業内容
- 施設・空間の計画（図面・イメージ）
- 運営の内容、年間プログラム
- 実施体制と役割分担

## 5. 地域との連携
- 連携する団体、既に得ている合意
  ※ **小さな担い手の最大の武器。ここを厚く書く**

## 6. 収支計画
- 初期投資と資金調達
- 年間収支（根拠となる需要推計を必ず添える）
- リスクと対応

## 7. 維持管理・持続性
- 体制、修繕、事業終了時の扱い

## 8. スケジュール
```

## 5. 小さな担い手が大手に勝つための7原則

1. **資金力で勝負しない。** 施設整備の規模で競うと必ず負ける。
   運営の質・頻度・地域密着で競う土俵に持ち込む。

2. **地域との既存の関係を可視化する。** 大手が最も持っていないのがこれ。
   協定書、連名の要望書、地元団体からの推薦状は、抽象的な熱意の
   100倍効く。**書類を作る前に、まず地元の合意を取りに行かせる**。

3. **上位計画を引用する。** 総合計画・個別計画の文言を引いて、
   「この提案は市の方針に沿っている」と示す。審査員（＝職員）にとって
   これは説明責任を果たしやすい提案になるという意味を持つ。

4. **前例を示す。** 他自治体の類似事例を具体的に示す。
   審査する側のリスクを下げることが、採択への近道。

5. **小さく始めて広げる設計にする。** 初期投資を抑え、段階的に拡張する
   計画は、実現性の評価で有利に働く。

6. **失格要件を最初に潰す。** 様式違反、期限、必要書類の不足。
   内容がどれだけ良くてもここで落ちる。提出2週間前にチェックする。

7. **数字を1つは入れる。** 「にぎわいを創出します」ではなく
   「年間48回、延べ3,000人の利用を見込みます」と書く。
   根拠が粗くても、数字がある提案の方が評価される。

## 6. 批判的レビューの観点

ドラフト完成後、**必ず審査員の立場で落とす理由を3点以上挙げる**。
褒めて終わってはならない。次の観点で検証する。

- 収支計画の前提となる需要推計に根拠があるか（「◯人来る」の根拠は何か）
- 実施体制の人員は実在するか、それとも「予定」か
- 初期投資の資金調達先が具体的か
- 事業がうまくいかなかった場合の撤退・原状回復の記載があるか
- 地域との連携が「これから話す」になっていないか
- 上位計画との整合が、こじつけになっていないか
- 建物を使う場合、用途変更・消防の適合を検討済みか（**未検討なら赤信号**）
- 配点の大きい項目に、相応の紙幅を割いているか

指摘したら、必ず補強案をセットで出すこと。指摘だけで終わらせない。
