# 成果物検証スキル（deliverable-verifier）

Claudeが作成した文書系成果物を、納品・提出前に検証し、指摘を反映した修正版まで仕上げる。

## 1. 基本姿勢（なぜこの手順なのか）

自分で作った成果物は、作成時の思い込みをそのまま引き継いで読んでしまう（作成者バイアス）。そのため、次の4点を守る。

1. 「確認した」と書けるのは、1次情報・計算・実行で実際に当たったものだけ。当たれなかったものは「確認不能」と書く。推測で埋めない。これがハルシネーション対策の核になる。
2. 好意的に読まない。「どこが間違っているか」「どの前提が崩れると結論が変わるか」を探す。指摘ゼロを目標にも、指摘数を稼ぐことも目標にしない。
3. 検証と修正を分ける。先に指摘を確定し、そのあとで修正する。同時に進めると、直しやすい指摘だけが拾われる。
4. 判断が分かれる論点（法令解釈、政策判断）は断定しない。複数の見方を並べ、確認すべき相手（所管課、法務、弁護士）を示す。

## 2. 対象と範囲

- 対象：企画書、報告書、提案書、説明資料、決裁・議会関連の資料案、メモ。形式は Word / PowerPoint / PDF / Markdown / チャット内の本文のいずれでもよい。
- 対象外：入力資料（他者が作った資料）の速読レビューは `doc-quick-review` を使う。HTMLダッシュボードやコード単体の検証は今回の対象外。依頼があれば観点A〜Dを準用し、コードは実際に実行して確認する。

## 3. 手順

### Step 0：準備と重要度の判定

集めるもの：①成果物本体、②元の依頼文（何を求められたか）、③適用すべき出力ルール（ユーザー設定・プロジェクト指示に書かれた形式・文体・フォント等のルール）。②③が手元にない場合は、成果物から読み取れる範囲で観点A〜Cを中心に進め、不足を報告に書く。

重要度を判定する。次のいずれかに当てはまれば「重要案件」（Step 3 の独立検証を行う）。

- 外部提出、決裁、議会、公表、登壇・講義、記事の公開に使う
- 法令・条例・判例・制度の記述を含む
- 予算・人員・数値を根拠に判断を求める
- ユーザーが「重要」「厳密に」「提出前」と述べた
- Step 2 で【致命】の指摘が1件以上見つかった（途中で重要案件に格上げする）

短いメモなど軽い文書は簡易モードにする：Step 1 の台帳を省き、観点A〜Dの要点だけを確認する。

### Step 1：主張台帳をつくる

成果物から、検証できる主張を抜き出して一覧にする。読み流さず、1文ずつ拾う。

| 種類 | 例 |
|---|---|
| 事実 | 組織名、制度名、事業名、経緯、固有名詞、事例 |
| 数値 | 金額、人数、割合、件数、面積、年次 |
| 日付・期間 | 施行日、年度、スケジュール、和暦と西暦 |
| 法令・判例 | 法律名、条番号、判決の日付と結論 |
| 出典 | URL、資料名、統計名、引用 |
| 論理 | 「Aだから Bである」「Bなので Cをすべき」という推論 |

台帳は検証作業用の中間成果物。最終報告には、必要な範囲だけを載せる。

### Step 2：自己チェック（全件で実施）

4観点で検証する。各主張に判定を付ける：**確認済**／**部分確認**／**誤り**／**確認不能**。

**観点A：事実・出典・法令**
- 1次情報に当たる。法令は e-Gov法令検索（https://laws.e-gov.go.jp/）、判例は裁判所の裁判例検索、統計は e-Stat（https://www.e-stat.go.jp/）、自治体・省庁の記述は公式サイトや公表資料。報道・まとめサイトだけで「確認済」にしない。
- 法令は「現行か」「施行日はいつか」「未施行の改正はないか」「条番号は合っているか」まで見る。手順と一次情報の場所は `japan-law-research`。
- **判例は、裁判所・判決日・結論を、判決文で確認する。** 確認できない判例は「誤り」ではなく「確認不能」とし、修正版では削除する。実在しない判例の引用は【致命】。
- 自治体の事実は、川崎市は `kawasaki-admin-reference`、東京都・横浜市は `metro-gov-reference` の確認済みの内容と突き合わせ、確認日が古いものは原文で再確認する。
- 出典 URL は実際に開いて、書かれた内容が本文の記述と一致するかを見る。リンク切れ、内容の不一致、出典が見つからない記述は指摘にする。
- 組織名・役職・制度名・事業名は、成果物の日付時点で正しいかを見る（改称、分離、統合、廃止）。
- 海外・国内の事例は、実在、時期、規模、結果を1次情報で確かめる。

**観点B：論理の整合性**
- 成果物の中の矛盾：数値、用語、日付、固有名詞が箇所によって違っていないか。
- 推論の連鎖：現状 → 課題 → 原因 → 方針 → 具体策 → 効果、の各つなぎ目に飛躍がないか。
- 根拠の不足：結論を支える根拠が、結論の強さに見合っているか。因果と相関の混同、少数事例の一般化、前提の未記載はないか。
- 見落とし：検討されていない代替案、反対側の論点、実現上の制約（法制度、予算、人員、合意形成、期間）はないか。
- スケジュール：工程の順序と所要期間が現実的か。依存関係の漏れはないか。
- 「この前提が崩れたら結論はどう変わるか」を最低1つ考え、報告に書く。
- 構成の点検: 見出しだけを通読して話が通るか。結論・根拠・裏付けをピラミッドに書き起こせるか。書き起こせない所が論理の穴（`logic-storyline` の点検表と誤りの型）。
- データ分析に基づく主張: 相関を因果として書いていないか、比較相手は妥当か、件数は足りるか、評価指標は適切か（`data-science-foundations` のレビューの点検表）。

**観点C：数値・計算**
- 合計、割合、増減率、年度換算、単位、桁を、手計算でなく Python などで再計算する。
- 表・図・本文で同じ数値が一致しているか。グラフの値が元データと合っているか。
- 年度（4月〜翌3月）と暦年、和暦と西暦、税込と税抜、名目と実質の混在がないか。
- 推計や仮定に基づく数値は、仮定が明示されているかを見る。
- 事業収支・VFM・利回りは、前提（単価、割引率、期間、時点）を表から拾い、再計算する。前提を動かしたときに結論が保たれるかを見る（`urban-development-practice`）。

**観点D：指示への適合と体裁**
- 元の依頼文の要求（論点、分量、対象読者、形式）を全部満たしているか。
- 適用すべき出力ルールに照らして確認する。ユーザー設定やプロジェクト指示にある最新のルールを優先する。よくあるルールの例：
  - 冒頭に簡易な日本語の「概略」、続いて「詳細」の順になっているか
  - 専門用語に注釈があるか。図表を使って説明しているか
  - 根拠と出典が示され、参照したサイトのリンクが全て出力されているか
  - 客観的な整理のあとに、主観的な意見が分けて書かれているか
  - Word・PowerPoint は本文10.5pt以上で、見出しが階層ごとに大きくなっているか
  - HTML は、スマホでダーク・ライトどちらの背景でも見やすいか
  - 「わからない」ことが、わからないと書かれているか
- 誤字脱字、表記ゆれ、体裁崩れ（表の欠け、改ページ、図の欠落）。ファイルは実際に開いて、見た目まで確認する。

### Step 3：独立検証（重要案件のみ）

作成者の文脈を持たない別エージェントに、検証だけを任せる。作成者の推論過程と Step 2 の結果は渡さない。渡すと、同じ見落としを引き継ぐため。

Agent ツールが使える場合は、次の内容で起動する。観点を分けて並列に走らせてもよい（例：A と C を担当するエージェント、B と D を担当するエージェント）。

```
あなたは検証担当です。下の成果物を、作成者の意図を好意的に推測せず、誤りと弱点を探す立場で検証してください。成果物は修正せず、指摘だけを返してください。

【成果物】<ファイルのパス、または本文>
【元の依頼】<依頼文>
【適用する出力ルール】<ルール>
【検証観点】A 事実・出典・法令（1次情報に当たる。Web検索可）／B 論理の整合性／C 数値・計算（再計算する）／D 指示への適合と体裁
【判定の付け方】各指摘に、観点、重大度（致命／重要／軽微／提案）、箇所、内容、根拠（URLまたは計算過程）を付ける。確認できなかった主張は「確認不能」とし、理由を書く。確認できたものだけを「確認済」とする。
【返す形式】指摘一覧（表）、確認済の主張の一覧、確認不能の主張の一覧。
```

Agent ツールが使えない環境では、独立検証はできない。その場合は成果物を最初から読み直す形で2周目の自己チェックを行い、報告に「独立検証は未実施」と明記する。

### Step 4：突合して指摘を確定する

| 状況 | 扱い |
|---|---|
| 自己チェックと独立検証の両方が指摘 | 確度が高い。そのまま確定 |
| 独立検証だけが指摘 | 自分の見落としの可能性が高い。優先して1次情報で再確認し、確定する |
| 自己チェックだけが指摘 | 独立側の見落としの可能性があるため、根拠を再確認して確定または取り下げる |
| 両者の判定が食い違う | 1次情報または再計算で決着をつける。決着しなければ「確認不能」とする |

重大度の基準：
- **【致命】** 誤りのまま使うと、意思決定、法的判断、対外的な信用が損なわれる（法令の誤り、金額・件数の誤り、結論を覆す論理の破綻）
- **【重要】** 結論は変わらないが、説得力・正確性が大きく下がる（出典の不一致、根拠不足、重要な代替案の欠落）
- **【軽微】** 表記ゆれ、誤字、体裁
- **【提案】** 誤りではないが、改善すると質が上がる点

### Step 5：修正版をつくる

- 元のファイルは上書きしない。`<元の名前>_検証済み_YYYYMMDD.<拡張子>` のように、別名で保存する。元と同じ形式で作る（docx / pptx / pdf は、それぞれの形式用のスキルを読んでから作る）。
- 誤り：1次情報に基づいて訂正し、出典を併記する。
- 確認不能：削除するか、「（要確認）」を付けて断定表現を弱める。推測で数値や事実を補わない。
- 論理の飛躍：根拠を補う。補えないときは主張を弱める。それでも解決しない場合は、修正せず報告に残す。
- 体裁・ルール不適合：ルールに合わせて直す。
- 方針や結論そのものを変える修正は、勝手に行わない。報告に「修正案（要承認）」として書く。
- 変更履歴は、成果物の本文に混ぜない。検証報告の側に書く。

### Step 6：再検証と報告

- 修正版に対して、数値の再計算と、修正で新たに入れた記述の出典確認を行う。修正が新しい誤りを生むことがあるため。
- 報告は次の順に出す。会話内では「1」と「2」を示し、指摘が多い場合は「3」以降をファイルにまとめる。

```
1. 概略（簡易な日本語で）
   総合判定：提出可／要修正（修正版で解消）／要判断（承認が必要な論点あり）／差戻し
   指摘件数：致命 n／重要 n／軽微 n／提案 n
   最も重要な指摘を、3件以内で
2. 要判断の論点（修正案・要承認）と、確認不能で残した事項（理由つき）
3. 指摘一覧（表）：ID／観点／重大度／箇所／内容／根拠・出典／修正内容
4. 確認済みの主な事項（何に当たって確認したか）
5. 検証の方式と限界（独立検証の実施有無、確認できなかった範囲）
6. 出典一覧（参照したURLを全て、リンクつきで）
```

## 4. 検証の限界は隠さない

次のものは、検証しきれない。報告の「検証の方式と限界」に必ず書く。

- 非公開情報、内部資料、有料データベースにしかない情報
- 検証時点より後に起きた法改正や制度変更
- 解釈が分かれる法令・判例の評価（弁護士や所管課の確認が必要）
- 独立検証ができなかった場合（Agent ツールが使えない環境）

「全て確認済み」と言い切れるのは、台帳の全項目に判定が付いたときだけ。1つでも判定が付いていなければ、そのことを書く。
