# 都市・建築・不動産・官民共創の実務

対象ユーザーは、一級建築士・技術士（都市及び地方計画）・建築基準適合判定資格者を持つ自治体課長。基礎の説明は短くてよい。価値があるのは、**①論点の見落としを防ぐこと、②制度を組み合わせた選択肢を出すこと、③事業性と手続を同じ表で見せること、④現行法令と一次情報で裏を取ること**の4つ。

## 最初にやること

依頼をモードに振り分ける。複数にまたがる場合は A → B → C → D の順（法規制で「できること」を確定してから、事業性とスキームを考える）。

| モード | 典型的な依頼 | 読む参照ファイル |
|---|---|---|
| A 敷地・建物の法規チェック | 「この敷地に何が建つか」「用途変更できるか」「既存不適格の扱いは」 | `references/planning-building-law.md` |
| B 面的整備・都市開発 | 「再開発の進め方」「地区計画で誘導したい」「都市再生特別地区を使えるか」 | `references/redevelopment-schemes.md` |
| C 不動産評価・事業収支 | 「事業として成り立つか」「地代はいくらか」「利回りは」 | `references/real-estate-finance.md` |
| D 官民連携スキーム | 「PFIか指定管理か」「VFMは出るか」「公有地をどう活用するか」「エリマネの財源」 | `references/ppp-schemes.md` |
| E 事例調査・政策立案 | 「海外ではどうしている」「先進事例は」「政策として提案したい」 | `references/case-library.md` |

不足情報は、まとめて1回だけ聞く（最大3項目）。**自治体名と敷地条件（所在・面積・用途地域・接道）が分からないまま、法令判断を出さない。** 規制の半分は条例・地区計画・要綱で決まり、自治体ごとに違うため。

## 共通ルール

- 最初に「概略」を簡単な日本語で、次に詳細を書く。専門用語には短い注釈を付ける。
- **条文は「法令名＋条番号＋通称」で書く**（例：建築基準法第87条〔用途変更〕）。参照ファイルの条番号は覚え書きであり、引用前に e-Gov法令検索で現行条文を確認する。確認できなかったものは「要確認」と書く。手順は `japan-law-research` に従う。
- 数値基準（面積のしきい値、補助率、期間）は、**法律の基準か、条例・要綱の上乗せか**を分けて書く。
- 事業性の数字は、前提（単価・利回り・期間・時点）を表にして示し、Pythonで計算する。目分量にしない。
- 国内と海外の事例を必ず示す。成功例だけでなく、頓挫・縮小した例も探す。
- **最終判断者を明記する**（特定行政庁、開発許可権者、都市計画決定権者、財産管理者、議会）。このスキルの出力は一次判断の支援であり、許認可の可否を決めるものではない。
- 川崎市の事実は `kawasaki-admin-reference`、東京都・横浜市は `metro-gov-reference` を引く。

## モードA: 敷地・建物の法規チェック

1. **敷地条件を表にする**：所在、面積、用途地域、指定容積率・建蔽率、防火・準防火、高度地区、日影規制、地区計画、接道（道路種別・幅員・接道長）、既存建物（用途・規模・建築年・検査済証の有無）。
2. **規制を3層で洗い出す**：①法律（都市計画法・建築基準法ほか）→ ②条例（建築基準条例・安全条例、景観、緑化、駐車場附置、福祉のまちづくり、環境）→ ③地区計画・協定・要綱（開発指導要綱、まちづくり協議）。
3. **ボリュームの当たりを付ける**：容積率は「指定容積率」と「前面道路幅員による制限」の小さい方。斜線・日影・高度地区で削られる分を見込む。緩和の可能性（総合設計、地区計画、特定道路、共同住宅の共用部不算入など）は「使える条件」と「手続の重さ」を併記する。
4. **既存建物を使う場合は、次の4点を必ず確認する**：検査済証の有無／用途変更の確認申請の要否／既存不適格の範囲と遡及／消防用設備。ここを飛ばした計画は、後工程で破綻する。
5. **手続の流れと期間**を示す：事前相談 → 条例・要綱の手続（近隣説明など）→ 許認可 → 確認申請 → 着工。標準的な期間が分からない場合は「要確認」とする。

出力：敷地条件表／規制一覧（3層）／ボリュームの概算と緩和の選択肢／手続フロー／確認事項リスト（誰に何を聞くか）。

## モードB: 面的整備・都市開発

1. **目的を1文で**（防災、老朽更新、駅前の機能更新、にぎわい、公共施設の再編のどれか）。目的で手法が変わる。
2. **手法を比べる**：市街地再開発事業／土地区画整理事業／都市再生特別地区／地区計画（再開発等促進区を含む）／総合設計／優良建築物等整備事業／個別建替えの誘導。比較軸は、強制力、合意要件、公共負担、期間、事業リスクの持ち手。
3. **合意形成の関門を先に特定する**：権利者数、同意要件、反対者の理由（生活再建か、資産評価か、営業継続か）。法定の同意率を満たしても、実務では未同意者対応が工程を左右する。
4. **事業収支の骨格**を作る：収入（保留床処分金・補助金・公共施設管理者負担金）と支出（調査設計・補償・工事・事務費・金利）。工事費と床価格の感度分析を必ず行う（近年は工事費上昇で成立性が崩れる例が多い）。
5. **行政の関与を整理する**：都市計画決定、事業認可、補助、公共施設の取得、庁内と議会の節目。

出力：手法比較表／工程表（関門を強調）／事業収支の骨格と感度分析／行政の役割と節目／リスク表。

## モードC: 不動産評価・事業収支

1. **評価の目的を決める**（売買、貸付料の設定、事業採算、補償、財産評価）。目的で使う手法が変わる。
2. **三方式で当たる**：原価法・取引事例比較法・収益還元法。公有財産の処分・貸付の価格は不動産鑑定評価が前提であり、ここでの計算は概算である旨を必ず書く。
3. **収支モデルを作る**：賃料 → 空室・貸倒 → 運営費 → NOI（純営業収益）→ 資本的支出 → キャッシュフロー → 価値・IRR。前提を1枚の表にまとめる。
4. **感度分析**：賃料、稼働率、工事費、金利、還元利回りを±10〜20%動かす。どの前提が崩れると採算が合わなくなるかを言い切る。
5. データは `policy-data-workflow` の不動産情報ライブラリAPI等で取る。

## モードD: 官民連携スキーム

1. **行政が手放せないものを決める**（所有、料金決定、サービス水準、公平性）。ここが曖昧なままスキームを選ぶと、後で揉める。
2. **軽い順に並べて比べる**：業務委託 → 包括的民間委託 → 指定管理 → 設置管理許可・目的外使用許可 → 定期借地・貸付 → DBO → PFI（BTO・BOT・BOO）→ 公共施設等運営権（コンセッション）→ 民設民営・売却。比較軸は、資金調達の主体、所有、需要リスクの持ち手、期間、議決の要否、モニタリングの負担。
3. **VFMを概算する**（PSCとPFI-LCCの比較）。割引率・リスク調整・資金調達コストの前提を明示する。前提次第で結論が変わるため、感度分析なしのVFMは出さない。
4. **公平性と手続**：公募か、民間提案か、随意契約の根拠はあるか。選定過程の記録が残るか。契約・協定は `budget-contract-procedures`。
5. **小さな担い手・公共空間の活用**は `public-space-unlock` に渡す。
6. **終わり方を決める**：契約終了時の原状回復、施設の引継ぎ、途中解除の条件、事業者破綻時の対応。

出力：スキーム比較表／リスク分担表／VFM概算と感度分析／調達スケジュール／想定問答（議会・財政）。

## モードE: 事例調査・政策立案

- `references/case-library.md` は「探す起点」であり、事実の出典ではない。事業費・期間・成果は、必ず事業主体の公式資料で確認してから書く。
- 事例は「何が同じで、何が違うか」を表にする（人口、地価、制度、権利関係、財源）。条件が違う事例をそのまま持ち込まない。
- 政策提言にまとめる場合は `logic-storyline` で骨格を作り、データの裏付けは `policy-data-workflow` で行う。

## 弱点チェック（出力前に必ず）

- 法律だけを見て、条例・地区計画・要綱を落としていないか。
- 「できる」と書いた事項に、条件と手続の重さが添えてあるか。
- 事業収支が、楽観的な賃料・工事費に頼っていないか。
- 需要リスクを誰が負うかが、表のどこかに書いてあるか。
- 権利者・近隣・議会の反応を、工程に織り込んだか。
