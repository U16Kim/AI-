# モデル・エフォート判定スキル

## 目的
ユーザーは、指示を実行する前に「どのモデルで、どのエフォートが適切か」を知り、自分で切り替えてから本実行したい。
だから **このスキルでは依頼内容そのものを実行しない**。判定を返して止まる。
(理由: 先に実行すると、判定を見て切り替える意味がなくなり、トークンも無駄になる。)

ユーザーが「そのまま実行して」と明言した場合だけ、判定を1行添えて実行に進む。

## 選択肢
- モデル: Haiku 5.5(軽量・高速) / Sonnet 5.5(標準) / Opus 5.5(高性能) / Fable 5.2(最上位。最も重く、最も高精度)
- エフォート: low / medium / high / xhigh / max

選択肢はこのリストに限る。上位ほどコスト・時間が増えるため、「迷ったら最上位」にはしない。過剰も不足も損失になる。

## 手順
1. 指示文を読み、下の7軸を各 1〜3 点で採点する(1=低、2=中、3=高)。
2. 合計点と「加点・上書きルール」から推奨を決める。
3. 下の出力形式で返す。実行はしない。

### 7つの評価軸
| # | 軸 | 3点になる例 |
|---|---|---|
| A | 論理の深さ | 多段の推論、矛盾の指摘、戦略立案、制度設計 |
| B | 正確性の重要度 | 法令・条例・判例・財政・統計の厳密な記述、公文書に使う |
| C | 情報収集量 | 1次情報のweb調査、複数資料の突合、事例の国内外比較 |
| D | 成果物の規模 | 長文レポート、複数ファイル、HTMLダッシュボード、スライド一式 |
| E | あいまいさ | 目的・条件が不明で、解釈や聞き返しが必要 |
| F | 作業の長さ | ツールを何度も使う、コード実行・検証を繰り返す |
| G | やり直しの難しさ | 外部送信、上書き、削除、公開など、取り消しにくい操作 |

### 点数の目安(合計 7〜21点)
| 合計 | モデル | エフォート |
|---|---|---|
| 7〜9 | Haiku 5.5 | low |
| 10〜12 | Sonnet 5.5 | low〜medium |
| 13〜15 | Sonnet 5.5 または Opus 5.5(下の「切替ポイント」で決める) | medium〜high |
| 16〜18 | Opus 5.5 | high〜xhigh |
| 19〜21 | Fable 5.2 | xhigh〜max |

### 上書きルール(点数より優先)
- B(正確性)が3点 → 最低でも Opus 5.5 / high。法令・行政の誤りは実害が大きく、あとで直すコストが高いため。
- E(あいまいさ)が3点 → 重いモデルより先に「聞き返し」が効く。モデルは据え置き、「先に条件確認が必要」と明記する。
- G(やり直しの難しさ)が3点 → エフォートを1段上げる。ミスの代償が大きいため。
- 定型作業(要約、書式変換、誤字修正、単純な関数の作成)だけなら、点数が高くてもエフォートは上げすぎない。
- `max` は「失敗した場合の損失が大きく、かつ論理が複雑」なときだけ。多用しない。

## Sonnet 5.5 → Opus 5.5 の切替ポイント
合計点が 10〜15 のとき、または迷ったときは、次のチェックで決める。
理由: Sonnet は大半の実務をこなせる。Opus に上げる価値があるのは、「浅い推論だと見落とす」「間違いのコストが高い」場合だけ。

### A. 1つでも当てはまれば Opus にする(強い条件)
1. 法令・条例・判例・制度の根拠を厳密に書く(公文書、議会答弁、報告書の根拠部分)
2. 3つ以上の資料・事例・データを突き合わせ、矛盾や論点を自分で見つける必要がある
3. 「私の主張の矛盾・甘さを徹底的に指摘して、最適な方針を示す」型の批判的検討
4. 政策の基本方針・具体的方策・スケジュールを、ゼロから論理立てて組み立てる
5. 機械学習・統計の手法選定から実装・結果解釈まで一貫して任せる
6. 外部送信・上書き・公開など、取り消しにくい操作を含む

### B. 2つ以上当てはまれば Opus にする(弱い条件)
- 出力が長い(目安: A4で3ページ以上、またはスライド10枚以上)
- 国内外の事例調査を複数件、1次情報で裏づける
- コードが複数ファイルにわたる、またはデバッグ原因が不明
- 指示にあいまいな点があり、解釈を自分で補う必要がある
- 読み手が上位者・議会・外部機関で、表現の精度が評価に直結する

### C. 当てはまっても Sonnet のままにする
- 書式変換、要約、誤字修正、表の整形、翻訳、定型メール
- 単一ファイルの小さなコード修正、SQL・Excel関数の作成
- 英会話練習(Sonnet / medium で十分)
- すでに骨子が決まっていて、文章化・体裁づくりだけの作業
(A に該当しても、C が主作業でA該当部分がごく一部なら、その部分だけ後から Opus で確認する)

### 切替の判定と出力への反映
- A が1つ以上 → 「Opus 5.5 に切替」と明記し、該当した項目の番号と理由を書く。
- B が2つ以上 → 「Opus 5.5 に切替」。1つだけなら「Sonnet 5.5 / high で開始。出来が不十分なら Opus へ」と書く。
- どれにも当たらない → 「Sonnet 5.5 のまま」。
- 判定結果の「詳しい理由」に「切替ポイント: A○ / B○ / C○」の形で必ず記載する。

## ユーザーの業務の傾向(判定の補助)
この利用者は、政策・事業の企画提案、行政資料、報告書、データ分析コード(Python/R/SQL/QGIS)を多く依頼する。
- 法令・条例・行政制度を含む → Bを3点にする。
- 国内外の事例調査・1次情報の確認を含む → Cを2〜3点にする。
- HTMLダッシュボード・Office資料の作成 → Dを2〜3点にする。
- 単純なコード修正・データ整形 → 低めに採点する。
- 英会話練習 → Haiku/Sonnet・low〜medium で十分。

## 出力形式(必ずこの順)
簡易な日本語で書く。専門用語には注釈をつける。

```
## 判定結果(概略)
- 推奨モデル: ○○
- 推奨エフォート: ○○
- 難易度: ★☆☆〜★★★(一言で)
- 先に確認が必要: あり / なし

## 採点表
| 軸 | 点 | 理由(1行) |
|---|---|---|
| A 論理の深さ | | |
| B 正確性 | | |
| C 情報収集量 | | |

## 詳しい理由
- なぜこのモデルか
- なぜこのエフォートか
- 上書きルールを使った場合はその説明

## 代替案
- コスト優先の場合: ○○ / ○○
- 精度優先の場合: ○○ / ○○

## 次のアクション
推奨設定に切り替えたあと、同じ指示をもう一度送ってください。
(E が3点の場合は、先に確認したい点を箇条書きで3つ以内で示す)
```

## 注意
- 判定は経験則に基づく目安であり、モデルの実際の性能差を保証するものではない。この点を判定の末尾に一言添える。
- 指示文が短すぎて採点できない場合は、無理に採点せず、不足情報を聞き返す。
- 判定の対象は「ユーザーが次に送る指示」。このスキルを呼び出す文そのもの(「判定して」)は対象にしない。
