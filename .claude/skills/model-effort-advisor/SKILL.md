# モデル・エフォート判定スキル

## 目的と原則
ユーザーは、指示を実行する前に「どのモデルで、どのエフォートか」を知り、自分で切り替えてから本実行したい。
- **依頼内容そのものは実行しない。** 判定を返して止まる。先に実行すると切り替える意味がなくなるため。
- 「そのまま実行して」と明言された場合だけ、判定を1行添えて実行に進む。
- 判定は **Yes/No のゲート** で機械的に決める。点数の足し算はしない(同じ指示で毎回同じ結果になるように)。

## 選択肢
- モデル(軽い順): Haiku 5.5 → Sonnet 5.5 → Opus 5.5 → Fable 5.2
- エフォート(浅い順): low → medium → high → xhigh → max
- 上位ほどコスト・時間が増える。「迷ったら最上位」にはしない。

## 大原則: 「モデルを上げる」と「エフォートを上げる」の使い分け
失敗の原因で決める。

| 起こりそうな失敗 | 対処 |
|---|---|
| 考えが浅い、検討漏れ、論理の飛躍 | **エフォートを上げる**(同じモデルのまま) |
| 知識が足りない、構成力不足、長文で一貫性が崩れる、表現が粗い | **モデルを上げる** |
| 両方が起こりそう | モデルを1段上げ、エフォートも1段上げる |

エフォートはモデルより安く切り替えられる。先にエフォートを上げ、それでも足りない場合にモデルを上げる。

---

## ステップ1: モデルを決める(下から順にゲートを通す)

### ゲート1: Haiku 5.5 → Sonnet 5.5
次の **どれか1つでも Yes** なら Sonnet 以上。全部 No なら Haiku 5.5。
- [ ] 文章を新しく組み立てる(要約・整形・翻訳以外)
- [ ] コードを書く・直す(1行の修正や定型の関数を除く)
- [ ] web検索や資料の読み込みが必要
- [ ] 日本語の公式文書・報告書の文体が求められる
- [ ] 手順が3ステップ以上ある

Haiku で十分な例: 誤字修正、箇条書きの整形、単純な翻訳、定型メール、用語の簡単な説明、英会話の軽い練習。

### ゲート2: Sonnet 5.5 → Opus 5.5
**A が1つでも Yes**、または **B が2つ以上 Yes** なら Opus 5.5。そうでなければ Sonnet 5.5。

**A(強い条件・1つで切替)**
- A1. 法令・条例・判例・制度の根拠を厳密に書く(公文書、答弁、報告書の根拠部分)
- A2. 3つ以上の資料・事例・データを突き合わせ、矛盾や論点を自分で見つける
- A3. 「私の主張の矛盾・甘さを徹底的に指摘して」型の批判的検討
- A4. 政策の基本方針・具体的方策・スケジュールを、ゼロから論理立てて組み立てる
- A5. 機械学習・統計の手法選定から実装・結果解釈まで一貫して任せる
- A6. 外部送信・上書き・公開など、取り消しにくい操作を含む

**B(弱い条件・2つで切替)**
- B1. 出力が長い(A4で3ページ以上、またはスライド10枚以上)
- B2. 国内外の事例を複数件、1次情報で裏づける
- B3. コードが複数ファイルにわたる、またはデバッグ原因が不明
- B4. 指示にあいまいな点があり、解釈を自分で補う
- B5. 読み手が上位者・議会・外部機関で、表現の精度が評価に直結する

**例外(Sonnet のまま)**: 作業の主体が書式変換・要約・翻訳・定型文・単一ファイルの小修正・SQLやExcel関数の作成・骨子が決まった後の文章化のとき。A に1つ当たっても、その部分がごく一部なら、全体は Sonnet で進め、該当部分だけ後から Opus で確認する。

### ゲート3: Opus 5.5 → Fable 5.2
次の **C が1つでも Yes**、または **D が2つ以上 Yes** なら Fable 5.2。そうでなければ Opus 5.5。
Fable は最も重く高コスト。「Opus で足りるのに使う」損失が大きいので、ゲートは厳しめにしている。

**C(1つで切替)**
- C1. 過去に Opus で同種の作業をして、品質が不十分だった(ユーザーがそう述べている)
- C2. 総合計画・事業構想・政策提言など、組織の意思決定の土台になる文書を、骨子から全体まで一貫して作る
- C3. A1〜A6 のうち3つ以上が同時に当てはまり、かつ成果物が外部公表・議会提出・契約など重い用途

**D(2つで切替)**
- D1. 前例のない問題設定で、既存の型(テンプレート)に当てはめられない
- D2. 数十ファイル規模、または数時間規模の連続作業(長いコード開発、大規模な資料群の分析)
- D3. 複数の専門分野(法・財政・都市計画・データ分析など)を横断して整合させる
- D4. 反対意見や批判を想定した多角的な検証(レッドチーム)まで求められる

---

## ステップ2: エフォートを決める(モデル決定後、上から順に最初に当たったもの)

| 順 | 条件(最初に Yes になったものを採用) | エフォート |
|---|---|---|
| 1 | 1ステップで答えが決まる、機械的な処理 | **low** |
| 2 | 通常の文章作成・コード作成で、判断は少しだけ必要 | **medium** |
| 3 | 多段の推論が必要、または正確性が重要(A1・A2・A3 のどれか該当) | **high** |
| 4 | 複数の制約が互いに影響し合う、自己検証・突き合わせが必須、長文で整合性を保つ必要がある | **xhigh** |
| 5 | 下の「max の条件」をすべて満たす | **max** |

**max の条件(すべて Yes のときだけ)**
- モデルが Opus 5.5 または Fable 5.2
- 失敗した場合の損失が大きい(公表・提出・取り消し不能)
- xhigh でも不十分になりそうな根拠がある(前例なし、または過去に xhigh で不十分だった)

**エフォートの補正**
- A6(取り消しにくい操作)があれば、1段上げる。
- 作業の主体が定型作業(ゲート2の例外)なら、1段下げてよい。
- 指示が短すぎて採点できない場合は、無理に決めず不足情報を聞き返す。

---

## ステップ3: あいまいさの確認(モデルより優先)
B4(あいまいさ)が強く、解釈が複数に割れて成果物が大きく変わる場合は、**モデルを上げる前に、聞き返す**。聞き返しは重いモデルより効果が高く、安いため。
- 「先に確認が必要: あり」とし、確認したい点を3つ以内で示す。
- 推奨は「確認後の想定」で出す。

---

## 出力形式(必ずこの順)
簡易な日本語で書く。専門用語には注釈をつける。

```
## 判定結果(概略)
- 推奨モデル: ○○
- 推奨エフォート: ○○
- 現在の設定から: 【変更不要 / モデルを上げる / モデルを下げる / エフォートのみ変更】
- 先に確認が必要: あり / なし

## どのゲートで決まったか
| ゲート | 結果 | 決め手 |
|---|---|---|
| 1 Haiku→Sonnet | Yes/No | 該当した項目と理由 |
| 2 Sonnet→Opus | Yes/No | A○ / B○(該当番号と理由) |
| 3 Opus→Fable | Yes/No | C○ / D○(該当番号と理由) |
| エフォート | ○○ | 該当した行と補正 |

## 詳しい理由
- なぜこのモデルか(失敗の原因が「考えの浅さ」か「構成力・知識」か)
- なぜこのエフォートか

## 代替案
- コスト優先: ○○ / ○○(その場合に起こりうる劣化)
- 精度優先: ○○ / ○○(その場合の追加コスト)

## 実行後の見直し基準(切り替え後に使う)
- 論理の飛躍・検討漏れがあった → エフォートを1段上げて再実行
- 表現が粗い、長文で矛盾が出た、知識の誤りがあった → モデルを1段上げて再実行
- 出来が十分 → 次回から、1段下げて試す(コスト削減)

## 次のアクション
推奨設定に切り替えたあと、同じ指示をもう一度送ってください。
```

## 注意
- 閾値(長さ、ファイル数、時間規模など)は経験則であり、各モデルの実際の性能差を検証したものではない。判定の末尾に一言添える。
- 対象は「ユーザーが次に送る指示」。このスキルを呼び出す文そのもの(「判定して」)は対象にしない。
- 現在のモデル・エフォートがわかるときは「現在の設定から」の行を埋める。不明なら「不明」と書く。
- ユーザーの業務は、政策・事業の企画提案、行政資料、データ分析コード(Python/R/SQL/QGIS)、HTMLダッシュボード、Office資料が中心。法令・行政制度を含む場合は A1 を、国内外の事例調査を含む場合は B2 を、まず疑う。
